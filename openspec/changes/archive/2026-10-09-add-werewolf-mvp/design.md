## Context

全新项目（无既有代码），目标是终端单机狼人杀：1 名人类玩家 + 5 个 LLM 玩家，6 人局（狼人 ×2、预言家、女巫、平民 ×2）。已确认的产品决策：

- 交互形态：终端 CLI（Python + rich）
- LLM 接入：OpenAI 兼容通用配置（base_url / api_key / model），启动时引导配置
- 第一版从简：不设警长/警徽，平票 = 无人出局，6 人局固定配置（后续版本再扩展）

核心矛盾：狼人杀的乐趣来自**信息差**与**表演**，而 LLM 天然倾向于"全知视角说真话"。设计必须保证：规则判定 100% 确定性（代码），LLM 只负责在其视角内的发言与决策。

## Goals / Non-Goals

**Goals:**

- 一局完整可玩的 6 人局：夜晚技能结算 → 白天发言 → 投票放逐 → 胜负判定，循环至终局
- AI 玩家"像人"：有性格差异、引用真实发言盘逻辑、立场前后连贯、永不泄密
- 玩家与 AI 信息公平：同一套视角过滤机制，玩家当狼人时也看得到队友
- 单局成本可控（约 60~100 次调用），等待过程有流式反馈
- 引擎与 LLM 解耦：换模型、离线调试（AI 回复 mock）不影响规则层

**Non-Goals:**

- 不做警长/警徽、平票 PK、猎人开枪链等进阶规则（第二版）
- 不做 Web/GUI 界面
- 不做联机多人
- 不做对局存档回放（日志仅作调试留存）
- 不做 AI 强度分级调校（先用统一 prompt 策略，观察后再调）

## Decisions

### D1. 架构分层：引擎全知且确定性，LLM 只做"表演"

```
┌─────────────────────────────────────────────┐
│ engine/  确定性状态机（全知）                  │
│  状态流转 / 技能结算 / 投票计数 / 胜负判定       │
└──────────────┬──────────────────────────────┘
               │ 视角过滤后的事件流（公开 + 私有）
┌──────────────▼──────────────────────────────┐
│ llm/agents.py  AI 玩家（只见其所见）           │
│  prompt 拼装 → 调用 → 解析 → 穿帮检测 → 回填    │
└──────────────┬──────────────────────────────┘
               │
┌──────────────▼──────────────────────────────┐
│ ui/terminal.py  渲染与输入（rich）             │
└─────────────────────────────────────────────┘
```

理由：让 LLM 裁决规则会穿帮（狼人自认输）且不可复现。引擎是唯一事实源，每个玩家（含人类）只收到自己视角的事件流。

备选：LLM 做裁判 —— 否决，不可控且成本翻倍。

### D2. 事件溯源式状态表示

游戏内一切以**事件流**表示（`events.py`）：公开事件（发言、投票结果、死讯）与私有事件（查验结果、狼队友揭示、用药）。引擎持有全量事件，每个玩家的"记忆"= 从全量事件中按视角过滤出的子集。

好处：视角隔离变成一个纯函数（`visible_events(events, player) `），测试容易，玩家与 AI 共用同一机制。

### D3. AI 输出统一为 JSON，发言与倾向同包

每次 AI 调用要求返回结构化 JSON，用 pydantic 校验：

```json
{"speech": "口语化发言", "suspect": 3, "mood": "紧张"}
```

- 发言（自由文本）与怀疑对象/情绪（结构化）同包返回，避免额外调用
- 解析失败自动重试（最多 2 次），仍失败则降级为"弃权发言"（跳过该轮），游戏绝不因 LLM 失败而中断
- 投票是独立时刻（所有人发言结束后），另一次结构化调用 `{"vote": 3}`

### D4. prompt 四层拼装

AI 玩家 prompt = 身份层 + 记忆层 + 情境层 + 输出格式层：

1. **身份层**：角色、胜利条件、队友（如有）、人设卡（姓名/性格/口癖，每局随机分配）
2. **记忆层**：过滤后事件流，发言带编号（`[#n] 名字(座位)：…`），要求引用必须使用真实编号，杜绝幻觉
3. **情境层**：当前昼夜、座位顺序、自己的历史发言与投票（要求连贯或解释转变）、被针对等情绪状态
4. **输出层**：JSON schema + 铁律（永不泄露视角外信息、口语化 ≤150 字、禁列表体）

狼人 AI 的发言定位为"表演好人视角的分析"，其私有信息（队友、刀口）仅供策略参考、严禁出现在 speech 字段——穿帮检测器兜底。

### D5. 穿帮检测器：规则匹配 + 警告重试

纯代码检测（正则 + 视角越权规则）：speech 中出现"我的队友/作为狼人/我验过"等超出其视角的表述即判定穿帮，携带警告重新调用一次，二次穿帮则替换为安全发言（"我保留意见，先听大家的"）。

不做 LLM 自查（成本且不可靠）。

### D6. 调用基本串行，流式渲染

白天发言按座位串行（后者需看到前者发言），夜晚技能按固定顺序唤醒（狼刀→查验→用药）。两狼共享一个"狼窝会话"统一产出刀口目标（省调用且保证一致）。所有 AI 生成过程流式输出到终端（rich Live），把等待变成观赏。

估算：一局 2~3 个昼夜 ≈ 夜晚 3~5 次 + 白天发言 6×N + 投票 6×N ≈ 60~100 次调用，单局 10~20 分钟。

### D7. 配置管理：首次引导 + 600 权限本地文件

`config.py` 启动时检查 `~/.llm_murder/config.json`（权限强制 600）：
- 不存在 → 交互式引导输入 base_url（默认 `https://api.deepseek.com/v1` 可改）、api_key（终端不回显）、model，随后发起一次最小连通性测试请求，通过才写入
- 存在 → 静默加载，提供 `--reconfig` 重新配置

api_key 只落盘到用户主目录，不进项目目录（避免误提交 git）。

### D8. 技术选型

| 选择 | 理由 | 备选（否决原因） |
|---|---|---|
| Python + asyncio | openai SDK 支持最好；串行流程中流式处理简单 | Node（前后端同构优势用不上）、Go（开发速度慢） |
| rich | 终端面板/颜色/流式 Live 渲染成熟 | Textual（交互复杂度超出 CLI 需求） |
| pydantic | 结构化输出校验 + 自动重试提示 | 手写解析（脆弱） |
| pytest | 引擎层单元测试（视角过滤、结算逻辑是纯函数，好测） | — |

### D9. 模块结构

```
llm_murder/
├── main.py            # 入口：加载配置 → 建局 → 主循环
├── config.py          # D7 配置管理
├── engine/
│   ├── game.py        # 状态机：run() 驱动昼夜循环与胜负判定
│   ├── roles.py       # 角色枚举、技能时序、6 人局配置
│   └── events.py      # 事件定义 + visible_events() 视角过滤
├── llm/
│   ├── client.py      # OpenAI 兼容客户端、重试、流式
│   └── agents.py      # AI 玩家：prompt 拼装、人设卡、解析、穿帮检测
└── ui/
    └── terminal.py    # rich 渲染、玩家交互（发言/技能/投票输入）
```

## Risks / Trade-offs

- [LLM 输出格式漂移导致解析失败] → pydantic 校验 + 最多 2 次重试 + 降级为弃权，绝不阻塞对局
- [AI 穿帮泄密] → prompt 铁律 + 规则检测器 + 安全发言兜底；接受 5% 级别的残余风险，记录日志便于调 prompt
- [单局 10~20 分钟内调用串行等待] → 流式输出把等待变成内容；发言字数上限控制时长
- [API 费用失控] → 单局调用次数可预估（60~100）；终端显示累计 token/费用估算（可关）
- [AI 立场摇摆、前后矛盾] → 喂回其历史发言/投票并要求连贯或解释转变；不追求完美，优先可玩
- [api_key 泄露] → 600 权限 + 存用户主目录 + 不回显输入；代码仓库内无敏感信息
- [模型不支持 JSON 模式] → 不依赖 response_format 强约束，用 prompt 约定 + 解析容错（提取 JSON 块）兼容各家
